Payment/cancellation coordination
booking_payment_controls is a durable record per booking. State is not_started, in_progress, accepted, failed, canceled or reconciliation. All payment RPCs and cancellation submission serialize on the booking, then ledger and control rows. Campaign operations take the campaign lock first. No transaction stays open during a Stripe call.

The service-only begin_payment_operation RPC acquires a two-minute fenced operation token before create, confirm, reconcile or cancel. Each phase reports verified provider state through finish_payment_operation. Concurrent callers receive busy. A process crash retains its identity; unknown create retries use the original zone-create-{charge_id} key only within a conservative 23-hour window. Confirmation keeps zone-initial-confirm-{charge_id}. There is never a replacement intent identity for this booking. Unknown identities outside the replay window require provider investigation; they do not authorize another create.

Cancellation submission permanently revokes that booking's collection authority and invalidates recovery links. It prevents ledger preparation, create/confirm and new secret exposure. Declining a request does not silently restore payment authorization. Previously exposed secrets or in-flight requests require provider reconciliation. The application makes no promise that a request already sent to Stripe was revoked. A known unpaid intent can be explicitly canceled through the gated reconciliation action. Success and processing require review; no automatic refund is implemented. A canceled/unknown authorization cannot be reused. Provider webhooks remain the source of truth for marking bookings paid; late success remains visible and auditable even when cancellation is pending.

A canceled reservation is recorded only if collection never started or Stripe confirmed cancellation, and no printer commitment exists. Otherwise admin cancellation returns requires_resolution, preserves inventory and records an alert. Cancellation requests cannot be marked resolved until the booking is actually canceled. Shared-card detachment still respects other reservations; all live detach writes are also blocked for this release.

Printer operations
Under a campaign's Advanced / Printer Records, upload a genuine document, then record each stage in order: submitted, accepted/committed, printed, submitted for mailing, confirmed mailed. No event means not submitted. Events retain the admin, timestamp, evidence and explanation. The server checks the stored file; SQL requires a matching private Storage object. These are records of externally verified events, not printer orders. Accepted/committed is the production commitment boundary and blocks automatic cancellation pending review. The record does not itself publish evidence or change customer-facing campaign status.

Checkout and email
The booking layout displays a neutral closed message. Shared hold, setup, consent and confirmation services and server actions enforce the gate; direct completion routes return 403. The only bypass is isolated development/test mode with localhost Supabase and no Vercel runtime. Production flags cannot enable it. Setup webhooks preserve existing reserved access without confirming a new gated checkout. Successful/duplicate Resend callbacks do not drain unrelated owner notifications. New adverse delivery events remain actionable.
