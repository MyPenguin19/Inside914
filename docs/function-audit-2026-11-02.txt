Reported “Continue to artwork” failure
-------------------------------------
At the start of the audit, PUBLIC_CHECKOUT_RELEASED was false in
src/lib/checkout/release.ts.
holdAreas() refuses new holds before database or Stripe access when this gate
is closed. /book/layout.tsx also refuses checkout. The public selector previously
did not receive the gate's state, so it offered an active Continue button anyway.
Clicking it returned the exact “Reservations are not open yet” message reported
by the owner and cleared the selected squares. This happens before artwork upload.

Local correction: pass the server's checkoutReleased() result to the selector.
Closed checkout allows an area/position preview, labels areas “Preview only,”
shows the closure before submission, and replaces Continue with a disabled
“Reservations not open yet” control. It does not create a hold or release checkout.
Server protections remain in place even if a client has stale UI state.

Owner approval follow-up: the owner approved the linked policies and saved-card
consent for new reservations, effective November 2, 2026. Current local source
uses 2026-11-02-reservations-1 and enables normal reservation checkout. Previous
versions and accepted records remain unchanged. The closed-state UI/guards are
retained and tested for a future source withdrawal. Collection remains disabled.
See docs/legal/2026-11-02-reservation-approval.txt for the exact scope.

Additional confirmed failures corrected locally
---------------------------------------------
1. A rejected/network-interrupted hold request escaped the React transition and
   could crash the selector. It now preserves selected positions, explains the
   interruption, and allows retry or return to held areas. It deliberately does
   not claim that the server made no hold: a response can be lost after a write.
2. The selector could submit a stale selected slot after refreshed availability
   marked it unavailable. Continue now requires a currently available selected
   slot in every selected campaign. The database still arbitrates booking races.
3. A cropper event containing zero, NaN, or infinite dimensions crashed image
   previews with “Image and destination dimensions must be positive.” Both
   editors now ignore unusable transient crop geometry and retain the last valid
   crop. The house editor also uses one stable callback and avoids identical
   state updates. No print dimensions, upload bytes, crop policy, or server
   validation changed.
4. Removed the owner-rejected “Verified Mail” promotion: header navigation,
   homepage section/cards, verification FAQ and related footer slogan. Ordinary
   campaign progress, printer records and production-proof safety checks remain.
   Homepage mobile/desktop screenshots were inspected; widths 375 and 1440 match
   document scroll width, with no browser errors and no Verified Mail links.
5. Repaired fresh local setup and explicitly separated historical test data;
   see the bootstrap verification below. No historical migration was edited.

One earlier E2E run entered the house-editor error boundary after a screenshot/

How the repository works
------------------------
Next.js App Router provides public pages, private customer token routes, admin
pages, server actions and webhook/download endpoints. React components use the
existing shared UI primitives. Supabase stores zones, editions, ten-slot square
inventory, bookings/claims, artwork metadata, operations, email outbox and payment
ledgers. Public catalog reads use an anonymous client under RLS. Admin access
requires Supabase Auth plus an admins membership; actions call guarded admin RPCs.

Booking starts with chosen areas and positions. Server actions validate them,
then database functions atomically create timed holds. Private storage receives
artwork through authorized upload tickets. Customers can share artwork or edit
each area separately. Contact/consent precedes a Stripe SetupIntent to save a card;
it does not charge immediately. Existing reservations use private capability links,
not advertiser accounts. Per-campaign collection is a separate disabled operation
behind readiness checks, an idempotent ledger, account binding and webhook handling.

Email payloads enter durable queues; workers retry and signed Resend webhooks
update delivery state. Contact sends to the fixed owner inbox. Print exports load
authorized originals, use the campaign's immutable V1/V2 layout, and composite
customer art, permanent house art and path-based placeholder glyphs with Sharp.
Postal exclusion and readiness labeling are separate from downloading a preview.
