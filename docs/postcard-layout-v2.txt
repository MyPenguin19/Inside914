Inside914 postcard layout V2 — local implementation and release notes
Prepared 2026-10-23 on feature/postcard-layout-v2

The customer story is area selection -> a specific paid position in each area ->
original artwork and an approved placement -> business details -> save card with
$0 due today. Administrators review those same positions and download native
800-DPI front/back PNGs. This change does not authorize or trigger collection.

Completed application changes

* One canonical V2 definition: src/lib/print/layout-v2.json. The registry in
  src/lib/print/layouts.ts resolves a campaign's immutable layout_template.
  Application templates, reserved regions, artwork dimensions and print exports
  use this model. The migration contains a generated copy of the same JSON; a
  drift test compares it byte-for-value after JSON parsing. DB slot coordinates
  are generated from that payload, not from a second handwritten grid.
* New campaigns use amazingmail-9x6-v2. The existing square_v1 identifier remains
  the BUSINESS model ($399, ten positions), not the physical geometry version.
* Customer and administrator inventory maps use stored, validated slot geometry
  with no decorative padding inside the paid placement. Labels F1-F6/B1-B4 and
  numbers 1-10 remain stable. House/postal areas are non-interactive regions.
* Four booking steps, per-area artwork, simultaneous multi-area holds, price,
  consent terms, saved-card flow and explicit campaign controls are preserved.
* V2 uploads default to containing the full original. Customers can explicitly
  preview a crop and approve it before saving. Shared image-fit math is used by
  CSS previews and Sharp exports. No source image is resized or overwritten by
  positioning or exporting. Reusing an image in another area makes an independent
  copy and requires reviewing that area's placement.
* Front and back placement dimensions and effective resolution are shown. The
  minimum for mailing/collection readiness remains 300 effective DPI, calculated
  for the contained image at its actual physical size. Approximate full-panel
  minimums: front 834x834, back 688x845. Upsampling cannot add source detail.
* Settings supports V1 and V2 house crop proportions. V2 output is 2990x1986;
  existing normalized V1 2990x2086 house artwork remains usable without reupload.
  When proportions differ, the existing artwork is contained on the neutral
  background. Missing, corrupt or non-normalized house artwork retains the safe
  preview fallback and cannot make the campaign ready to mail.
* Front/back downloads are available at any fill level. Incomplete campaigns
  remain PREVIEW — NOT READY TO MAIL. Exporting cannot open a campaign, approve
  a proof, mark it mailed or charge a customer.
* Homepage illustration and terminology now show six front positions and explain
  the mixed placement offering, rather than advertising a retired 16-space card
  or claiming all new placements are square. Existing design tokens are reused.

Versioning and preservation

* amazingmail-9x6-ten-square-draft remains the historical V1 layout: 2.5-inch
  squares, original slot UUIDs and coordinates. Its original spec and tests are
  retained. No migration updates editions, slots, bookings, artwork, prices,
  payment references, consent records, dates, statuses or campaign history.
* The existing guard_square_campaign keeps an edition's physical version fixed.
  There is no automatic in-place upgrade, including unused V1 drafts. Create a
  new future V2 campaign explicitly; active V1 reservations continue in V1.
  Do not duplicate current campaigns or move an existing booking between them.
* A campaign's saved key determines its preview/export. Unknown keys fail closed
  instead of silently rendering the latest template. New app code supports both
  V1 and V2. Existing historical print evidence files are not rewritten.
* House artwork retains the established global behavior: replacement changes
  future downloads and invalidates earlier final proof approval. It is not a
  per-campaign snapshot. For exact historic CONTENT reproduction, retain the
  previously downloaded PNGs/published proof and prior house storage object.
  Layout versioning guarantees physical placement, not global-artwork freezing.

Database change

New additive migration:
  supabase/migrations/20261023035620_postcard_layout_v2.sql

It was applied transactionally to 127.0.0.1:54322 only. The local migration ledger
predates several manually applied migrations; schema verification, not ledger
version alone, establishes local state. No hosted schema was read or modified.

The migration:
* Widens four slot-coordinate columns from numeric(5,3) to numeric(8,6). Without
  this, 2.2925 would round, violating exact geometry. Values and UUIDs are retained.
* Saves and recreates the two dependent catalog views with their existing SQL,
  security_invoker=true and read grants. No CASCADE or data-table drop is used.
* Adds private.postcard_layout_versions (RLS on; no public/client/service grants)
  with the canonical V2 payload; provides private.square_slots(template_key).
* Registers the exact V2 key in private.approved_layout_templates with a detailed
  reservation-geometry approval reference. Existing guard_campaign_layout and
  application approval checks remain. This is not a final printer-proof approval.
* Keeps the ten-position/$399 checks and immutable inventory triggers, adding
  validation for the exact V2 geometry. A house/postal/eleventh position cannot
  be added to a square_v1 campaign by manipulating the client.
* Makes crop/resolution validation version-aware. Existing proof freshness,
  approved-artwork, payment consent, real payment method, full-zone, closed-zone,
  authorization, successful-charge and mailing readiness conditions remain.
* Creates no new public RPC signature. Public generated TypeScript DB types do
  not require changes. Private helpers use empty search_path and explicit grants.
* Does not change any RLS policy, storage bucket, Stripe integration or webhook.

Rollback guidance

An unsuccessful migration is rolled back as one transaction; no partial column,
view or function change should remain. Before any V2 campaign exists, a previous
application can still serve V1 on this additive schema, provided V1-compatible
house artwork is retained. Prefer leaving the additive schema in place.
Once V2 campaigns/holds/reservations exist, DO NOT deploy an older application
that only knows V1, delete the V2 registry, shrink numeric precision, or relabel
those campaigns as V1. Keep V2-compatible readers and issue a forward fix. Any
status changes require owner approval; no automatic closure/cancellation rollback.

Printer and USPS blockers

The nominal geometry passes. Final printer acceptance still needs confirmation
of the exact product/template, exclusion anchor, bleed/trim/safety tolerances,
stock/thickness, postal service, address/barcode/indicia handling, output format,
RGB-to-CMYK color handling/profile, effective source resolution and the final
customer/combined-house proof. Files contain a blank white exclusion and no
invented address, stamp or postal indicia. PNG outputs use 800-DPI metadata and
native 7300x4900 composition; printer acceptance of these files is separate.

USPS DMM 143 section 2.5a requires an EDDM Retail piece to exceed 10.5 inches in
length OR 6.125 inches in height OR .25 inch in thickness (and meet other limits,
including weight). A 9x6 finished card does not satisfy the first two criteria.
Its .0625 bleed is removed and must not be counted. Thickness/service has not
been confirmed; this product is not certified EDDM Retail compliant. Ask the
printer/mail house which supported mailing service applies before launch.
Official source: https://pe.usps.com/text/dmm300/143.htm
