Status
Implemented locally with isolated database and simulated Stripe verification.
Real Stripe test-mode payments, declines and 3-D Secure verification are blocked
because no local Stripe test keys/webhook signing secret were supplied. This is
not a production-ready or live-payment approval. Collection defaults to disabled.

Behavior
- An admin previews ten separate $399 obligations and explicitly authorizes one
  zone. The database locks the campaign and its bookings, verifies ten confirmed
  reservations, distinct normalized categories, single-slot claims, $399 consent,
  saved customer/payment method, approved square artwork, a printer-approved
  layout, a published final proof and a mailing window. Other zones are untouched.
- Exactly one durable ledger and one PaymentIntent per reservation. Initial intent
  creation and confirmation use stable, different idempotency keys. Intent ID is
  persisted before off-session confirmation. Failed/authentication-required
  intents are not automatically reconfirmed by admin retries.
- An ambiguous creation older than 23 hours is blocked for reconciliation rather
  than risking reuse after Stripe's idempotency retention window. Canceled intents
  also require administrator review; no replacement intent is silently created.
- Webhooks retain raw-body signature verification. Payment events are separate
  from SetupIntent reservation events. Live payment events cannot enter local
  test collection. The server retrieves the current PaymentIntent and verifies
  amount, currency, customer, booking, zone and ledger metadata before updating.
- A transactional event ledger handles duplicates and stale events; success is
  final. Only signed webhook processing marks the booking charged or failed.
  Payment state and authorization are audited. In-flight cancellation/inventory
  release/review changes are blocked; printing is blocked while payments remain.
- Failed payments/authentication requirements receive a three-day recovery-link
  window. Random 256-bit tokens are stored as hashes, rotate on reissue, and are
  consumed on success. URL tokens are exchanged for HttpOnly SameSite cookies,
  with no-referrer/no-store responses. Expired links require admin review.
- Recovery handles authentication on the same PaymentIntent or mounts the
  Payment Element for a replacement payment method. It never creates another
  charge. Already-issued Stripe client secrets are Stripe capabilities; the
  three-day limit controls access to the recovery link, not Stripe's intent expiry.
- Receipt/recovery notices are queued uniquely in the existing outbox. For this
  local-only phase, processing writes .dev-emails previews and marks them as
  not delivered; it never sends these payment notices through Resend.
- Admin campaign/production panels show test collection, state and recovery.
  Payments shows actual recorded Stripe-test totals and all card-sharing zone
  reservations, including members without their own SetupIntent ID.
- Existing components/styles are reused. Reservation checkout still charges $0.
