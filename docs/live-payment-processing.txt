Implementation
- Every ledger now has a Stripe mode and an optional account binding. New
  collection binds all ten obligations to a verified account before processing.
  Bound rows cannot change mode/account. Historical unbound rows remain test-only
  and cannot be rebound after any intent or processing state exists.
- Live binding requires launch-priced bookings. The service-only binding RPC
  locks the campaign; browser/admin clients cannot call it directly.
- Before creating a payment, the server checks the actual Stripe account, saved
  customer mode, payment-method mode and customer ownership. Existing intents
  must match the frozen ledger, amount, currency, customer and metadata.
- Live/test processing shares the per-booking idempotent PaymentIntent workflow.
  No new intents are created for recovery; ambiguous creation older than 23 hours
  still requires reconciliation. Signed events retrieve current Stripe state.
- Webhook processing rejects wrong modes/accounts, including connected-account
  events. The SQL recorder now checks account and mode before invoking the
  private transactional state machine. Duplicate events and succeeded status
  remain protected. Public/service access to the unscoped recorder is revoked.
- Recovery route, page and administrator link generation validate ledger mode
  and account. The existing Payment Element/authentication flow has correct live
  wording while retaining test labels for test records. Tokens remain hashed,
  expiring, rotated on reissue and consumed on success.
- Receipt and recovery notices use the existing outbox and sender. Live notices
  use HTTPS recovery URLs; test notices only create local previews. Receipts
  require succeeded status. Stale recovery notices for paid bookings are suppressed.
  Each notification uses a stable outbox idempotency key. Any attempted delivery
  failure requires manual reconciliation; it is not automatically resent with a
  rotated link. Disabled collection leaves payment notices queued without using
  their delivery attempts.
- Payments totals exclude test charges from live revenue; rows identify their
  mode. Existing components, layout and design are retained.
- A future release also requires the production runtime, HTTPS database/app URLs,
  matching live key prefixes, launch pricing and no simulated reservations.
  Environment changes cannot bypass the current hard-coded release gate.
