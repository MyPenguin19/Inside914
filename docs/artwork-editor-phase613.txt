Confirmed diagnosis
With the owner's read-only permission, the already-open production Settings page showed:
- Selected source: 495 × 619 pixels.
- Zoom: about 1.16; selected crop: approximately 426 × 283 source pixels.
- Required V2 house crop: at least 1122 × 745 pixels (300 effective PPI).
This image genuinely cannot satisfy the minimum, even at minimum zoom. The previous
"zoom out" message did not distinguish a small original from an over-zoomed crop.
The production page and selected file were not edited, reloaded or submitted.

Local boundary testing also caught a border-box measurement problem in the revised
cropper container: a 1122 × 745 image was reported as 1120 × 744. The editor uses an
inset visual ring instead of a dimension-changing border. The exact minimum now saves
successfully; neither client nor server quality requirements were reduced.

Other confirmed save/preservation defects
- Customer requestUpload deleted the current booking_artwork row and original object
  before the replacement finished uploading. Copying between areas also deleted the
  target's previous original immediately.
- Crop acknowledgement reset on every duplicate crop callback, including harmless
  cropper renders. A saved V2 crop could initially be labelled as full-image mode.
- The house route saved only a normalized PNG and discarded the source. Its error path
  removed a new file even when a lost RPC response might hide a committed activation.
- The house UI treated HTTP success plus router.refresh as proof of a successful save.

House editor
Current saved artwork stays at the top. Replace image opens file selection. A bounded,
neutral V2 preview supports drag/arrow keys, zoom and Reset. Save house artwork is the
single save action. The primary interface has no V1/V2 selector. Historical V1 rendering
and the V1-capable server normalization endpoint are retained.
The editor states original and crop dimensions, and distinguishes insufficient original
resolution from excessive zoom. Feedback covers uploading/saving, verification and
failure. PNG/JPEG and the 3 MB limit remain; server magic-byte/decode, pixel limits,
integer bounds, fixed ratio and minimum-resolution checks remain authoritative.

House save sequence
1. Validate original bytes and crop; generate the existing 800-DPI derivative.
2. Register a new private staged version with its original source dimensions/hash,
   crop, immutable layout key, and the previously displayed version timestamp.
3. Upload the untouched original and derivative to fresh, non-overwriting paths.
4. Read both objects back and compare exact bytes before activation.
5. An admin-only RPC locks the current version and rejects stale replacement attempts.
6. Verify the active database pointer. Return its version timestamp.
7. The browser fetches authenticated GET for exactly that version and decodes/checks its
   dimensions before showing success. The current image URL changes and Settings refreshes.
The existing house updated_at/proof-readiness relationship remains: a replacement affects
future downloads across campaigns and requires a new final proof before printing.
An ambiguous activation response never triggers destructive file cleanup.

Customer editor
V2 uses Upload → Adjust → Save artwork and continue.
Fit entire image is the default: the full source is centered, with neutral margins when
source and placement proportions differ. It never stretches or silently crops.
Fill space is optional: drag/arrow keys, zoom or touch pinch to adjust the crop. Explicit
acknowledgement is required only when source pixels are removed, and is tied to the rounded
source rectangle, not repeated callbacks. Changing Fit/Fill retains the working crop.
Reset and Replace image are the only secondary editing actions. A failed save leaves the
selected source and crop in place for retry. Existing V1 square-crop behavior is retained.
Quality feedback is plain language; exact source dimensions are secondary. Existing
customer warning thresholds and administrator PPI/readiness checks were not changed.

Replacement and retention guarantees
- Uploads are staged separately. The active booking source and crop remain unchanged until
  an explicit Save passes server validation and an atomic database operation.
- Save rechecks the hold capability, pending state, all cart siblings' expiry, crop bounds,
  V1 geometry rules, V2 crop consent, object existence, and concurrent replacement state.
- Crop changes store coordinates only. Customer originals are never resampled or overwritten.
- Copying to another area stages its own byte-identical object and requires that area's Save.
- Database triggers retain current/historical source references when artwork is replaced or
  removed. Previously saved originals and normalized house versions are never cleanup targets.
- Original house uploads go to the new private house-artwork-originals bucket; normalized
  print PNGs remain in the existing private house-artwork bucket.
- Admins can read the private version ledger. Ordinary signed-in users and anonymous users
  cannot read it or the source bucket. Activation still requires the existing admin check.
- Cleanup runs separately from email and payments, using CRON_SECRET. It atomically claims
  never-committed uploads older than 24 hours, excludes active references, prevents activation
  of claimed paths, and retries failed Storage removals without discarding tracking records.
  Signed upload URLs have expired by cleanup time. The daily job processes up to 100 records.

Retention limits and operations
This cannot reconstruct originals discarded before this change, or recover previously deleted
customer uploads. Existing normalized house files remain usable. Untracked legacy Storage
objects are not guessed to be garbage and are not automatically deleted. Recovery of retained
versions is an authenticated operational task; a history/restore UI is intentionally not added.
Unsaved replacements are temporary stages, not a cross-session draft product. Leaving the
editor keeps the prior saved image; never-saved stages become cleanup-eligible after 24 hours.
Retained originals consume storage intentionally. Monitor cleanup claimed/removed counts and
backlog; increase job capacity if sustained abandoned uploads exceed its batch size. An outage
may delay deletion; it must not result in deletion of a valid source. Rolling back to the old
application would reintroduce its destructive replacement behavior, so do not use that as a
casual rollback while artwork uploads are active.

Geometry and renderer consistency
No approved geometry, crop/contain renderer, postal exclusion or 800-DPI export values changed:
V2 front 2.78 × 2.78 in; back 2.2925 × 2.815 in; house 3.7375 × 2.4825 in.
V1 historical geometry remains. Final output remains 7300 × 4900 PNG with 800-DPI metadata.
The customer preview uses integer source crop coordinates, as Sharp does, and the existing
shared containImage calculation. A browser raster comparison checks the V2 Fit preview against
an actual Sharp B1 panel, with a small tolerance for browser rasterization. House preview exports
are checked against exact renderer pixel hashes. Existing V1/V2 rendering tests also pass.
A text-formatting fix rounds displayed placement dimensions to avoid floating-point tails;
it does not change stored or rendered dimensions.
