Prepared 2026-10-23 on feature/campaign-management-pricing

1. Layout mismatch: findings and limits

The hosted migration registry contains V2, but installing a template does not
upgrade existing editions or their stored slots. The read-only production audit
found five editions, all using amazingmail-9x6-ten-square-draft (V1), at $399.
The generic homepage illustration uses V2; it is not a campaign inventory view.
The campaign selectors, inventory maps and PNG renderer already resolve the
edition's saved layout key. Therefore a V2 illustration and a V1 campaign can
legitimately show different geometry. No campaign-specific screenshot URLs/IDs
were supplied for this request, so their identity cannot be conclusively matched.

The campaign detail also lacked an assembled-artwork view. AssembledSide could
fall back to legacy dimensions unless its caller supplied dimensions, and did
not render permanent house artwork. It now derives dimensions from the same
layout registry and is mounted on the campaign detail with real placements and
validated house artwork. Visible campaign ID/version and export response headers
make customer/admin/export comparisons traceable.

2. Public labels and print consistency

The public house region says only Reserved, centered, neutral and noninteractive.
Assistive technology identifies it as a reserved, nonbookable region. The postal
region remains excluded. Administrator previews and exports retain house artwork.
Both V1 and V2 use their own stored positions; no geometry constants were changed.
The existing crop/contain transform avoids stretching square originals into V2
rectangles. Unapproved artwork is clearly marked in the administrative preview.
PNG downloads remain the actual renderer output, not browser screenshots.
V2 front/back are 7300 x 4900 pixels at 800 DPI (9.125 x 6.125 inches).
X-Campaign-Id and X-Layout-Key identify the exported edition and template.

3. Administrator workflow

The campaign list offers Active, Draft and Archived filters. Rows show area/month,
layout version, current position price, status, reserved/total positions, approved
artwork, mailing status and edit/manage actions. Active means not archived and
includes finished campaigns until the owner explicitly archives them.
Detail pages show the assembled front/back and existing inventory/print controls.
Delete, archive and upgrade are separate, authenticated, audited actions.

4. Custom pricing and accepted-price safety

Price per advertising position ($) defaults to 399 and accepts positive amounts
with up to two decimal places. The database stores integer cents. Creation and
editing use the same validator; the database validates again. Price edits are
allowed after holds/reservations exist, without unlocking dates or layout.
Only subsequent holds use the new edition price. Each existing hold/reservation
keeps bookings.price_cents, and a trigger prevents rewriting that agreed price.
The hold RPC compares the submitted amount with the locked campaign record.
Multi-area totals, consent, checkout and reservation email use stored amounts.
Payment summaries, notices, recovery and eventual collection use the immutable
booking/consent/ledger amount, never the campaign's latest advertised price.
The ledger rejects mismatched consent and later changes to its amount/identity.
No price edit invokes Stripe, collects money or issues a refund.

5. Permanent deletion

Only an unarchived draft with no booking of any status, payment consent, charge,
mailing evidence or layout-upgrade history is eligible. Because artwork belongs
to a booking, artwork history also blocks deletion. DELETE CAMPAIGN is required.
The server rechecks eligibility under a campaign lock, removes only safe empty
inventory and the edition, and retains a snapshot in admin_events. Direct table
deletion cannot bypass the guard. Retrying an already completed deletion is safe.

6. Archiving

Only cancelled or completed campaigns can be archived, with ARCHIVE CAMPAIGN.
Archive is not cancellation: the existing cancellation/payment-method cleanup
and notification workflow must complete through its normal rules first.
Archiving does not change terminal status, bookings, artwork, payments, evidence
or consent. It hides the campaign from default active lists, preserves detail
access through Archived, and cannot make the campaign bookable again.

8. Optional V1-to-V2 upgrade

Existing V1 campaigns need no conversion to remain usable and reproducible.
Moving a chosen campaign to V2 requires a separate owner-approved operation.
The admin dry run checks the exact ten canonical positions, campaign state,
active holds, payments and mailing history and displays the mapping/warnings.
An open campaign must first be paused explicitly; active holds must expire or
finish. Collection ledgers, advanced payment states and mailing activity block
the upgrade. A changed snapshot invalidates the dry run.

UPGRADE TO V2 plus a fresh fingerprint invokes one transaction. It preserves
all ten slot IDs/labels, booking IDs and ownership, agreed prices, saved payment
methods, Stripe references, original files and crops. Only approved canonical
V1-to-V2 geometry changes are allowed through a private transaction capability;
ordinary geometry edits remain forbidden. Existing artwork approval is reset,
and prior final-proof records remain historical evidence but cannot approve V2.
Private campaign_layout_history preserves pre-upgrade inputs, and admin_events
records the action. Neither API clients nor service_role can rewrite that history.
Retries are idempotent. The workflow does not reopen the campaign or call Stripe.

12. Remaining approvals

Owner approval is required for the production migration/rollout and separately
for each production V1 campaign pause/upgrade/resume or price/status change.
Converted placements need renewed artwork approval and a new final printer proof.
Existing files uploaded to AmazingMail/Xpressdocs do not update automatically.
Printer confirmation, replacement upload and any mailing order remain separate.
LIVE_COLLECTION_RELEASED remains false; collection mode remains disabled.
Live collection requires separate approval after all release/payment checks.
No production data, campaigns, reservations, environment settings or Stripe
objects were modified by this implementation task.
